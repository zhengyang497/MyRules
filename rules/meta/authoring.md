# 怎么写规则

本文件不同步到项目。改 `rules/user/` 或 `rules/project/` 之前先读完。

可下发的规则只住在那两个目录。草稿和事故原委放在 `staging/`。同步安全（保护名单、漂移、prune）在 skill 的 `REFERENCE.md` 里，不要抄进这里。

## 三把尺子

### 1. 黄金测试

每加一行或留一行，先问：删掉它，模型会不会更容易犯错？会，就留；不会，就删。规则一发胀，真正要紧的条目会被一起忽略。

「写可维护的代码」「小心 prompt」这类空话，以及删了也不改变行为的句子，都过不了这关。过期的也删：代码里已经修死、流程已经变、staging 里标了过期。

### 2. 见过再写

加约束，要对应你亲眼见过的模型失误。删约束，是因为模型已经强到这条显得多余。为想象中的失败写预防条款，通常是噪声。

例外是不可逆的灾难，比如删掉无法恢复的数据。这种情况优先做自动检查（Sensor），不要只靠条文劝模型听话，并写明你是故意打破「先看见再写」。项目里已经有检查时，不要再补一句含糊劝告：要么写出确切命令，要么就靠检查本身。

### 3. 双极

真实失败是必要的，但不够。只补刚听到的那一头，对面那头会变容易。「太长了，所以以后永远要短」就是这类错。事故过程记在 `staging/articles/`，这里只留做法。

增、扩、删之前：

1. 重读整份目标文件，不要只看正在改的那一段。
2. 先写出对面那头的失败；写不出，就还不能改。
3. 新句子必须让对面那头也更难发生。一句撑不住两头，就停，不要再贴一条单向补丁。
4. 不要把一次事故写成整文件的 always、never、all。约束收在失败所属的那类情境。
5. 已经堆了一串单向补丁，就收成一段能管两头的文字，不要再贴第四条。

删条目也走同一套：不能因为上一篇太长，就把「不要口号」删掉。

## 语体

可下发的规则用中文写，按中文组织句子，不要先写英文再译。意思要准，句子要顺，读起来像中文写成的说明。专业判断、术语、分点都可以留。

整句检查，不要逐词排查。词都认得，仍可能是翻译腔或说明书腔。也不要为了通顺改成聊天口吻。分点里的句子仍用通顺书面中文，不要写成决议稿，也不要写成口语速记。不要拿「句子宜短」当标准，那会收成碎句。

规则正文是模型会跟着学的样本。语体含糊，回复也会含糊。怎么跟用户说话仍写在 `communication.md`；本文件只管改规则时怎么落笔。

这一段自己也有两头：说明书长句不像中文；改成大白话又不专业。新句子必须让这两头都更难发生。

反例：「和股票代码表一样，放项目下的 `.llm-wiki` 里一份 JSON（开不开、页路径、预算），桌面和命令行读同一份。」  
正例：「放在项目的 `.llm-wiki` 下，和股票代码表同类，不进 wiki 正文。设置里改完，桌面导入和命令行都读这一份。」

## 放哪里

`rules/user/` 是所有角色都要的个人规则，不要写 `agents:`。  
`rules/project/` 可以按角色收窄。好的条目具体、可执行，并能说明沉默为什么危险。

`project/` 可用：

```yaml
---
agents: [implementer, reviewer]
---
```

| `agents` | 规则频道 | 子代理包 |
|----------|----------|----------|
| 省略 | 仍全量加载 | 跳过并告警；补上明确列表 |
| `all` | 全量加载 | planner、implementer、reviewer 都带 |
| `[planner]` 等 | 全量加载 | 只进列出的角色 |

Frontmatter 在部署前会剥掉。角色固定为 planner、implementer、reviewer。

## 改完怎么走

先修眼前的问题。同一轮里不要打开对应规则文件往上贴补丁。先写下这一头和对面那头，再写成能管两头的句子。

```
文章或事故 → staging/articles/ → staging/merge-queue/into-*.md
  → user/ 或 project/ → push.js → sync.js
```

不是每条笔记都该变成可下发规则。怎么写规则只放在本文件，不要写进沟通或行为规则。每个可下发文件保持精瘦，大约不超过 300 行；变长就按主题拆，或把叙事挪到 `staging/articles/`。

消费项目用同步出来的 `myrules-*`。要它自动生效：改缓存，再 push，再 sync。
