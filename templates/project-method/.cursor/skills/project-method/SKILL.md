# 项目工作法

先读 [`docs/方法/项目工作法.md`](../../../docs/方法/项目工作法.md)。模板、看板命令与逐步核对见 [reference.md](reference.md)。

人拍板意图和取舍，并习惯说「先登记」。你查代码事实、把口语收成标准条目、用 `npm run board` 登记和改状态、现场写进这张卡、做检查清单同步和守门。人说审计时按流程五三阶段做。不准手改卡片页眉。不准因为耗时长就新开《功能名设计目标》。不准把尚未做成的句子或做法细节写进文首。不准把对话里的新目的直接写进代码当现行标准。不准把卡片目录或讨论文稿当收件箱。

## 第零步：先有看板项

还要被找回来的工作，动代码之前必须有一个 `item-N`：

1. 已有进行中的项就 `npm run board -- get --id item-N` 点名它，需要时 `--set focus=true`。
2. 没有就 `npm run board -- add --title "..." [--body "..."] [--focus]`。只要标题和几句说明。不要因为当时说不清落点而拒绝登记。不要预置需求/方案/实施三节。登记后现场在 `docs/看板/items/item-N.md`。
3. 用户只说「先登记」时：登记完停下，等他说开始再改业务代码。

一行能结束、不值得交代的小改，可以不登记，记在提交说明里。拿不准就问人要不要登记，不要自行开卡。

不要用 `--plan`，不要按文字长短把卡分成两种。

## 写进能力时：三步判断

改目的、或收工发现有现在就该能对质的长期句子，才问。不是登记手续。先问这句是目的还是做法。尚未做成的不要写进文首。做法（字段、路径、切篇、prompt 纪律）不要写进文首。

0. 这句是目的还是做法？拿掉它，产品要的那件事变了才算目的。做法 → 只关卡，收尾：没有。
1. 是否改了已经存在的长期承诺？→ 改那篇文首，同一轮同步检查清单；需要时 `--set placement=改承诺 --set goal=<路径>`。
2. 是否多了一句现在就该守住的新承诺？→ 能挂进现有那篇就挂；否则才新开一篇。需要时 `placement=新承诺`。
3. 做完即结束？→ 只把看板项标完成，不新开设计目标。

拿不准就摊开选项等人拍。

## 按情况进流程

| 情况 | 流程 |
|------|------|
| 目的或做成标准要改 | 流程一（先改文首和检查清单，再扫看板进行中的项） |
| 要借鉴另一个现成系统 | 流程二 |
| 开始写或改还要被找回来的代码 | 流程三（已有 item-N；现场写在这张卡；对照做成标准给证据；收工前问长期规则并写下收尾行） |
| 设计目标里出现走查、日志、尚未做成的句子或做法细节 | 流程四（搬回对应那张卡） |
| 人要审计目标 | 流程五（done 项收尾 → 清单矛盾问人 → 干净清单对照代码和产物） |

改了任何一篇文首之后：

1. 把 `docs/设计目标检查清单.md` 对应行抄成与文首逐字相同。不在表上记未落地。
2. 扫描看板进行中的项，说明哪些仍有效、哪些该改范围、哪些该标完成或废弃。
3. 若目的句变了，同步 `.myrules-context.md`。

标 `done` 之前：问这张卡有没有拿掉就会换目的、现在就该能对质的句子。有 → 写入对应文首，同步检查清单。没有 → 只 `patch --status done`。无论有没有，都在这张卡正文写下单独一行「收尾：有」或「收尾：没有」。若还没定稿或还要再拆步骤，不要标完成。

## 空转自检

目的变了却先改业务代码、一次性重活却新开设计目标、未登记就改还要被找回来的工作、拿不准要不要登记却不问人就动手或自行开卡、登记因缺落点失败、张张卡强制三节模板、完成时只说编译过了或卡上没有收尾行、把走查、未做成的句子或做法细节写进文首、把切篇/字段/prompt 当成能力、把卡片目录当第二张工作台、另挂现行指针、或人说审计却跳过收尾去对照代码，都是失败。停下来按对应流程重做。
