# 项目工作法

这份说明书回答：人和模型怎么把一个个人项目做下去，又不把「要做到什么」写散。它本身不是验收表。目的变了，改各篇《功能名设计目标》的文首，不要改这篇——除非你改的是工作法本身。

## 出发点

个人项目不必在动手前把蓝图想死。目的往往在写了一段探路代码之后才变清楚。允许目的不全，也允许中途改。

不能妥协的是：一旦发现「其实我想要的是另一件事」，必须在同一轮把新说法写进全项目唯一允许写现行承诺的地方。对话里说清楚了不算落地。不写回就继续做，多头维护已经开始了。

## 总账领号，一卡一页，出口成能力

人只记一件事：还要被找回来的工作，先有编号。看板是总账加 focus：列上扫标题和状态，点开才是这张卡自己的一页。

每张工作就是一篇 markdown。正文可三句可三页，同一种卡。会话结束前，模型把下一步写进这张卡，而不是只留在聊天里。

产品承诺只在各篇《功能名设计目标》文首，而且只写**现在就该能对质的目的**。还没做成的放在对应那张卡里，不要写进文首假扮现行。做法（字段、路径、切篇、prompt 纪律）不是能力。

讨论文稿可以存在，只要它不是第二份收件箱、也不是第二份现行承诺。人从不去文件夹里挑今天干什么——从看板编号走进那一篇。

### 改进清单看板——总账和领号

每张卡一篇：`docs/看板/items/item-N.md`。页眉是编号、状态、focus、可选落点；下面是正文。编号和状态只经 `npm run board`（与 `npm run improvements` 相同）改页眉。正文按普通 markdown 改。页面用 `npm run board:server`。

常用命令：
- 摘要与当前项：`npm run board -- summary` / `npm run board -- next`
- 登记工作：`npm run board -- add --title "标题" [--body "说明"] [--focus]`
- 登记带落点：`npm run board -- add --title "改某承诺" --placement 改承诺 --goal docs/能力/某功能/某功能设计目标.md --focus`
- 改状态或摘 focus：`npm run board -- patch --id item-N --status done --set focus=false`
- 启动本地看板：`npm run board:server`（打开 http://localhost:8080/ 查看）

人已经养成的习惯——每次动手前让模型去看板登记——就是给工作领号。还要被找回来的工作，没有看板项 id（新建或点出现有项）之前，模型不动手。真正在干的项打 `focus`。

登记只要标题和几句说明，写进这张卡。当时不必填写改承诺、新承诺或只记工作。不预置需求/方案/实施三节。复杂正文用编辑器直接改该卡即可。

一行能结束、事后也不值得交代的小改，可以直接改，记在提交说明里。拿不准要不要登记时，先问人，不要自行开卡。人会说「先登记」。

### 《功能名设计目标》——出口成能力

每个以后还能被单独问起「这块做成了没有」的模块，一篇，放在 `docs/能力/<功能名>/<功能名>设计目标.md`。走查和某日记录写在对应看板卡上，不写进文首。

文首是现行做成标准：每条都能拿到现实里对质（拿什么材料、看哪里、怎样算没做成）。靠前的条目必须对着人要的那件事有没有发生。

文首写**目的**，不写做法。句子停留在「系统要保证什么」，不落字段、路径、切篇、prompt 纪律。检验：拿掉这句，产品要的那件事变了，才进文首；换一种做法目的还在，就只留在看板卡。实现细节可以写进正文「为什么这样 / 边界」，不进文首表。把做法写进文首，检查清单会胀。

程序拦住（接口合法、测试绿了）只有单独失败就会把**目的**打死时才进表，而且不得当第一条；拦住也要过「拿掉目的变了」这一关，不能把实现细节升成拦住。每条标明靠测试钉死还是靠人抽查。尚未做成的句子不进文首。

正文写为什么这样、边界在哪、明确不做的、若借鉴了别人则写清对方怎么做、为什么、我们认哪几项。文首才是承诺的措辞源头。

维护方式是原地替换。新决定改当前句子，至多用一行注明哪天为何改。禁止把这篇写成日记。

功能可大可小。该不该单独成篇，不看代码量，看三件事：以后会不会单独问这块做成了没有；做成标准能不能离开别的模块对质；这个名字会不会反复被叫起来。能，就单独成篇，哪怕现在很小。不能，就挂在已有那一篇下面。一篇里出现两套对不上的目的，就该拆，而不是继续撑大。切篇、命名、某张表的列，不够单独成篇，也不够单独占文首一行。

标完成时只做一件正事：看这张卡有没有拿掉就会换目的、并且现在就该能对质的句子。有，就写进对应文首（能挂已有那篇就挂，否则才新开），检查清单同一轮逐字抄上。没有，就只把卡片关掉。无论有没有，都在这张卡正文写下单独一行「收尾：有」或「收尾：没有」。若还没定稿、还要再拆步骤，状态就不该是完成。不要因为收工去另开一份脱离这张卡的计划。对话里问过不算收尾。对质的是目的发生没有，不是某字段在不在。

### 《设计目标检查清单》——全局巡检

全项目一份：`docs/设计目标检查清单.md`。把各篇文首的做成标准逐字收成表，列只要：编号、所属功能、目标原句、对比时看什么、验证方式、链回那篇文首。不含论证，不记某次对照结论，不记未落地。

人不要手改。改了某篇文首，模型必须在同一轮把对应行抄成一样。两处打架，以文首为准，立刻修表。需要总览时看这张表，不要穿梭十篇长文。不要人手维护第二份措辞不同的摘要。进度只看看板。

## 写进能力时：三步判断

这不是登记手续。改目的、或收工时发现有现在就该能对质的长期句子，才按这个顺序问。先问这句是目的还是做法。

**第零步：这句是目的还是做法？**  
做法（换一种做成办法，产品要的那件事仍在）→ 走第三步，只关卡，收尾：没有。过了再问改旧还是加新。

**第一步：是否改了已经存在的长期承诺？**  
是：改那篇文首，同步检查清单；看板上记下这次怎么落地，需要时补上 `placement` 为改承诺、`goal` 指向那篇。

**第二步：是否多了一句现在就该守住的新承诺？**  
是：先问属于现有哪一篇。属于就加进去；不属于才新开《功能名设计目标》。需要时补上 `placement` 为新承诺。新开的理由是多了一句要长期守住的目的，不是这次费事。尚未做成的不要为了占位而新开文首条目。

**第三步：做完就结束，以后不当作产品承诺来巡检？**  
是：只把看板项标成完成。换底层存储、大范围迁路径也一样。不为工作量大伪造长期承诺，也不把切篇、字段、prompt 升成能力。

两极都要防。什么都升成功能，检查清单没人巡检。什么都当琐事，决策只活在过期聊天里。中间一档的正规位置就是看板卡。

## 人和模型怎么分

人负责：提出和改目的；在路线之间拍板（采纳、砍掉、后置，理由指向自己此刻的需求，不能只说别人也这样）；审做成标准是不是目的（不是做法）、是否真是自己要的、是否现在就能对质；按「对比时看什么」抽检测试钉不死的实质结果。

人还负责：说出「先登记」或在模型提醒后确认开哪一项。这是已经养成的习惯，不要改成另一套记不住的入口。要核对应先说「审计」或「目标审计」。

模型负责：查代码里已经发生的事实，不拿猜测顶上去；把人口头说的收成区分实质结果与程序拦住的标准条目；用 `board add` / `board patch` 登记和改状态，禁止手改卡片页眉；现场写进这张卡的正文；改完文首后做检查清单同步，并扫描看板上进行中的项指出哪些还有效、哪些该改范围、哪些该标成完成或废弃；守门——人说先登记、或工作明显还要被找回来时，没有看板项就先登记再动手；小改可以不登记；拿不准就问人，不要自行开卡；登记不因当时说不清落点而卡住；收工时问有没有拿掉就会换目的、现在就该能对质的句子，并在卡上写下「收尾：有」或「收尾：没有」；人说审计时按流程五三阶段做，缺收尾行就停；新设计和已落地机制打架时列出冲突并停手；某篇设计目标混了两套目的时提议拆开；不准因为耗时长就擅自新开功能文档；不准把尚未做成的句子或做法细节写进文首。

搞懂一个外部做法不等于要搬进来。可以研究得很完整，同时一项都不抄。

## 五套流程

### 流程一：目的变了

1. 人说明新的理解，不必先写成文档格式。若还没有看板项，先登记，标题和几句即可。
2. 模型按三步判断（先过目的/做法关）：改旧篇文首、加进旧篇、还是新开一篇。起草文首修改（实质结果在前，拦住在后，标明验证方式；只写现在就该能对质的目的）。不先改业务代码。
3. 人确认措辞。
4. 模型原地替换那篇文首；同一轮逐字同步检查清单；必要时改 `.myrules-context.md` 里那句目的；扫描看板进行中的项，说明哪些继续、哪些改范围、哪些标完成或废弃。

### 流程二：要借鉴现成系统

不通盘翻译。只读打算搬的那一段：代码说明做了什么，提案、变更说明、提交记录说明为什么。推断标成推断，不要写成对方明文。

人逐项表态。每项理由指向本项目当前目的。模型拦住「因为对方也这样」当唯一理由。

拍板后写入《功能名设计目标》：文首是本项目现在就该能对质的做成标准，正文可附对照与取舍。立刻同步检查清单。学到的东西若改变了你要什么，先走流程一。

没有可对照的现成系统，整段不上。

### 流程三：动手写代码

人说「先登记」、或工作明显还要被找回来时，没有看板项 id 就先登记。拿不准就问人。现场写进这张卡。通读周围实现，把「改哪些文件、故意不做什么、下一步勾什么」写在卡上。有多种理解就摊开，不默默选。只改当次需要的行。无关的死代码可以记在卡上，不夹进当次必改。

做完对照关联的做成标准给两组证据，不准用「编译过了」代替做成：形式证据是测试命令、用例名和结果；实质证据是人拿什么材料、去哪看、怎样算目的发生了。人抽检实质结果之后，才把该项 `patch --status done`，并摘掉 focus。标完成前问：这张卡有没有拿掉就会换目的、现在就该能对质的句子。有则写入对应文首并同步检查清单；没有则只关卡。无论有没有，都在这张卡正文写下单独一行「收尾：有」或「收尾：没有」。

一行能结束、不值得交代的小改，不走本流程。

### 流程四：文档不要烂成日记

设计目标只保留现行标准、取舍理由与边界。调试、走查、临时配置、做法细节进对应那张看板卡。该项标成完成之后那些细节成为历史，不回写到文首。

发现设计目标已经在追加流水，或文首混了尚未做成的句子、做法细节，模型把过程段搬回对应项，并恢复文首只留现行目的。

### 流程五：项目目标审计

人说「审计」「目标审计」或「项目目标审计」时走本流程。三阶段按顺序，缺一段就停。结论写在对话里，不写进检查清单。

**第一阶段：收尾。** 只看 `status=done` 的项。每张卡正文必须有单独一行「收尾：有」或「收尾：没有」。缺这一行就列出来等人补，不进入第二阶段。不靠聊天记忆补「当时问过」。`wont` 和进行中的项不审。

**第二阶段：清单内部。** 通读《设计目标检查清单》。条目互相打架时摊开：哪两句不能同时为真、可能是目的改过还是写岔了。问人：留哪句、改哪句、拆成两篇，或确认暂时并存并写明为何。句子过具体、像做法（字段、路径、切篇、prompt）时同样摊开，问人删还是改回目的。人拍板后才改文首并同步检查清单。模型不擅自合并。曾经改过目的不是自动失败。

**第三阶段：对照现实。** 用当时干净的检查清单，逐条对照本仓库实现。人指定了产物路径（例如用模板新建的项目库）则一并对照；没指定就只审本仓库，不去猜隔壁目录。每条给出看了什么、是否做成；不准只用「编译过了」。

## 产出经过模型时再加厚

改生成规则不能凭「看起来更好」合入。锁住同一份输入、同一套参数、同一个入口；改前跑一次，改后跑一次；拿当天检查清单上的条目并排看，是否变好、有没有把别的打坏。目的若已改，样例也要能检验新目的。换模型时只换模型，不把提示词和参数一起改。

早期不必上复杂评测目录。一份固定样例、两次能复开的运行、并排放着看，就比凭感觉强。

## 新项目第一周

1. 同步个人规则（说话方式、证据、最小改动）。本工作法不代替那些。
2. 建 `docs/能力/`、`docs/方法/`、`docs/看板/`，写一句当前目的（`README.md` 与 `.myrules-context.md`）。
3. 放入本说明书、技能与项目工作法规则。通用红线走 MyRules 的行为规则同步，不写进本仓库。
4. 写第一篇《功能名设计目标》，文首只放现在就能对质的几条目的，不放做法。
5. 由模型生成检查清单，不要手抄。
6. 用 `npm run board -- add` 登记第一条，标题和几句说明即可，需要时加 `--focus`。现场写在这张卡上。

不要一上来建能力画像长卷、为每张卡预置三节空模板、讨论文稿文件夹当收件箱、或多份必须人手对齐的正文。能力变大、必须深入对照现成系统、或模型输出开始左右对错时，再按上面的流程加厚。

## 空转：骨架有没有配好

不必先写业务代码。用对话试这些事：

- 说「其实我想要的是另一件事」：应先改设计目标文首和检查清单，再问看板上哪些项还做，而不是直接改业务代码。
- 说「这次挺费事但做完就结束」：应只在看板登记，收工时不新开设计目标。
- 说「开始写这块功能」或「先登记」：没有看板项就先 `board add`；有项才亮明范围。现场写在这张卡上。登记不因缺落点失败。未登记就改还要被找回来的工作，算失败。
- 说「改个错字」或一行就能结束的修正：可以不登记。
- 说「去改一下」但看不出事后还值不值得交代：应先问要不要登记，不要自行开卡。
- 往设计目标里塞走查记录、尚未做成的句子或做法细节：应挪到对应那张卡，文首只留现行目的。
- 说「这项做完了」：应问有没有拿掉就会换目的、现在就该能对质的句子，并在卡上写下「收尾：有」或「收尾：没有」；不应把切篇、字段、prompt 写成能力，也不应去另开脱离这张卡的文件。
- 说「审计」或「目标审计」：应按三阶段做；done 项缺收尾行时应先列出来停下，而不是直接去审代码。

有一件直接动手、不走流程，就是常驻规则写长了被忽略，或技能描述没打中人的原话。把守门规则收短，把技能描述写得更像实际会说的那几句。
