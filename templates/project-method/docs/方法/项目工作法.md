# 项目工作法

这份说明书回答：人和模型怎么把一个个人项目做下去，又不把「要做到什么」写散。它本身不是验收表。目的变了，改各篇《功能名设计目标》的文首，不要改这篇——除非你改的是工作法本身。

## 出发点

个人项目不必在动手前把蓝图想死。目的往往在写了一段探路代码之后才变清楚。允许目的不全，也允许中途改。

不能妥协的是：一旦发现「其实我想要的是另一件事」，必须在同一轮把新说法写进目标册。对话里说清楚了不算落地。不写回就继续做，多头维护已经开始了。

目标比单个项目大。项目做完不等于目标做成。目标可以先是口号，不必有项目来承载。

## 两本账

**目标册**是各篇《功能名设计目标》的文首表。所有目标都在这里，包括口号。一条目标有：这句话要保什么、状态（口号 / 做了一截 / 已做成）、对比时看什么、验证方式、可选的项目编号（没有项目就空着）。

文首写**目的**，不写做法。句子停留在「系统要保证什么」，不落字段、路径、切篇、prompt 纪律。检验：拿掉这句，产品要的那件事变了，才进表；换一种做法目的还在，就只留在项目卡上。

状态不是「有没有卡」：

- **口号**：认这句，产品里还没发生。可以没有项目。
- **做了一截**：发生了一部分，整句还没做成。
- **已做成**：产品里这件事已经发生，以后按这句巡检；没发生就是退步。

总表从文首逐字抄，**必须抄状态**。口号和做了一截留在表上。不含论证，不记某次对照结论。

**项目卡**是还要被找回来的工作。有编号才是项目。卡可以引用目标编号，也可以不引用。关卡只表示这摊活结束，不自动改目标状态。

讨论文稿可以存在，只要它不是第二份目标册、也不是第二份收件箱。口号进目标册要人点头，不要从讨论文稿或聊天里爬进去。

## 总账领号，一卡一页

人只记一件事：需要领号时说「先登记」。不领号也可以直接改。看板不是所有改动必须经过的门；它只是总账加 focus：列上扫标题和状态，点开才是这张卡自己的一页。

每张已登记的工作就是一篇 markdown。正文可三句可三页，同一种卡。若当次有看板项，会话结束前把下一步写进这张卡，而不是只留在聊天里。没有看板项的改动，不必补开一张。

### 改进清单看板

每张卡一篇：`docs/看板/items/item-N.md`。页眉是编号、状态、focus、可选落点；下面是正文。编号和状态只经 `npm run board`（与 `npm run improvements` 相同）改页眉。正文按普通 markdown 改。页面用 `npm run board:server`。

常用命令：
- 摘要与当前项：`npm run board -- summary` / `npm run board -- next`
- 登记工作：`npm run board -- add --title "标题" [--body "说明"] [--focus]`
- 登记带落点：`npm run board -- add --title "改某目标" --placement 改承诺 --goal docs/能力/某功能/某功能设计目标.md --focus`
- 改状态或摘 focus：`npm run board -- patch --id item-N --status done --set focus=false`
- 启动本地看板：`npm run board:server`（打开 http://localhost:8080/ 查看）

人需要领号时说「先登记」。模型不要抢先开卡，也不要在改代码前先问要不要开卡。没说登记，直接改。

人要登记时：修 bug、补刀、同一块功能的后续，挂在相关旧项下面当子项（父项已 done 也可以）；没有子项机制就写进旧卡正文。不要另开一张同级父项。只有人说「开一项」、并且确实是一件新事，才 `board add`。真正在干的项打 `focus`。

登记只要标题和几句说明。当时不必填写改承诺、新承诺或只记工作。不预置需求/方案/实施三节。复杂正文用编辑器直接改该卡即可。

### 《功能名设计目标》——目标册的分组

每个以后还会被单独问起的产品面，一篇，放在 `docs/能力/<功能名>/<功能名>设计目标.md`。走查和某日记录写在对应项目卡上，不写进文首。

文首表才是目标的措辞源头。靠前的条目对准人要的那件事。程序拦住只有单独失败就会把**目的**打死时才进表，而且不得当第一条；拦住也要过「拿掉目的变了」这一关。每条标明靠测试钉死还是靠人抽查。口号阶段「对比时看什么」可以写尚未做成、现在没有材料。

正文写为什么这样、边界在哪、明确不做的、若借鉴了别人则写清对方怎么做、为什么、我们认哪几项。禁止把这篇写成日记。

功能可大可小。该不该单独成篇，不看代码量，看三件事：以后会不会单独问这块；目标能不能离开别的模块来看；这个名字会不会反复被叫起来。能，就单独成篇。不能，就挂在已有那一篇下面。一篇里出现两套对不上的目的，就该拆。切篇、命名、某张表的列，不够单独成篇，也不够单独占文首一行。

已挂在看板上的项目要关卡时，问三件事：碰到了哪条目标（没有就写只是做法）；若有，那条状态变了没有；然后关卡。旧卡上的「收尾：有」或「收尾：没有」仍算收尾。新卡可写「收尾：未碰目标」或「收尾：碰到 \<ID\>（\<状态\>）」。若还没定稿、还要再拆步骤，状态就不该是完成。不要因为收工去另开一份脱离这张卡的计划。

### 《设计目标检查清单》——目标册总表

全项目一份：`docs/设计目标检查清单.md`。把各篇文首逐字收成表，列只要：编号、所属功能、目标原句、状态、对比时看什么、验证方式、项目（可空）、链回那篇文首。

人不要手改。改了某篇文首，模型必须在同一轮把对应行抄成一样。两处打架，以文首为准，立刻修表。需要总览时看这张表。进度（哪摊活还在干）只看看板。

## 写进目标册时：三步判断

这不是登记手续。改目的、或收工时发现碰到了目标，才按这个顺序问。先问这句是目的还是做法。

**第零步：这句是目的还是做法？**  
做法（换一种做成办法，产品要的那件事仍在）→ 只关卡，不改目标册。过了再问改旧还是加新。

**第一步：是否改了已经在册上的目标？**  
是：改那句或改状态，同步总表。需要时补上 `placement` 为改承诺、`goal` 指向那篇。

**第二步：是否多了一句目标（含口号）？**  
是：先问属于现有哪一篇。属于就加进去；不属于才新开一篇。开不开项目是另一步，不是进册的条件。需要时补上 `placement` 为新承诺。

**第三步：这摊只是做法？**  
是：只把项目卡标成完成。换底层存储、大范围迁路径也一样。不为工作量大伪造目标，也不把切篇、字段、prompt 升成目标。

两极都要防。什么都升成目标，总表没人巡检。什么都当琐事，决策只活在过期聊天里。中间一档的正规位置就是项目卡。口号的正规位置是目标册，不是项目卡。

## 人和模型怎么分

人负责：提出和改目的；在路线之间拍板（采纳、砍掉、后置，理由指向自己此刻的需求，不能只说别人也这样）；审句子是不是目的（不是做法）、状态标得对不对；按「对比时看什么」抽检测试钉不死的实质结果。

人还负责：需要领号时说出「先登记」或「开一项」。不说也可以直接改。要核对应先说「审计」或「目标审计」。口号进册要人点头。

模型负责：查代码里已经发生的事实，不拿猜测顶上去；把人口头说的收成区分实质结果与程序拦住的标准条目；没说登记就直接改代码，不要先过看板；人要登记时用 `board add` / `board patch`，禁止手改卡片页眉；修 bug、补刀挂在相关旧项下当子项，不要另开父项；只有真正的新事才 add 父项；改完文首后做总表同步，并扫描看板上进行中的项指出哪些还有效、哪些该改范围、哪些该标成完成或废弃；收工时问碰到哪条目标、状态变了没有，并写下收尾行；人说审计时按流程五三阶段做；新设计和已落地机制打架时列出冲突并停手；某篇设计目标混了两套目的时提议拆开；不准因为耗时长就擅自新开功能文档；不准把做法细节写进文首。

搞懂一个外部做法不等于要搬进来。可以研究得很完整，同时一项都不抄。

## 五套流程

### 流程一：目的变了

1. 人说明新的理解，不必先写成文档格式。改目的不必先开卡，也不必先做成。口号可以先写入目标册。人说先登记才挂看板。
2. 模型按三步判断（先过目的/做法关）：改旧句或状态、加进旧篇、还是新开一篇。起草文首修改（实质结果在前，拦住在后；每条有状态、对比时看什么、验证方式）。
3. 人确认措辞和状态。
4. 模型原地替换那篇文首；同一轮逐字同步总表；必要时改 `.myrules-context.md` 里那句目的；扫描看板进行中的项，说明哪些继续、哪些改范围、哪些标完成或废弃。

### 流程二：要借鉴现成系统

不通盘翻译。只读打算搬的那一段：代码说明做了什么，提案、变更说明、提交记录说明为什么。推断标成推断，不要写成对方明文。

人逐项表态。每项理由指向本项目当前目的。模型拦住「因为对方也这样」当唯一理由。

拍板后写入《功能名设计目标》：进册的是目的，标状态。正文可附对照与取舍。立刻同步总表。学到的东西若改变了你要什么，先走流程一。

没有可对照的现成系统，整段不上。

### 流程三：动手写代码

没有看板项就直接改，不走本流程。人说动手、开工、修 bug，不等于要开卡。

已经挂在某张卡或子项上时：现场写进这张卡。通读周围实现，把「改哪些文件、故意不做什么、下一步勾什么」写在卡上。有多种理解就摊开，不默默选。只改当次需要的行。无关的死代码可以记在卡上，不夹进当次必改。人要登记修 bug 或补刀时，挂在相关旧项下当子项，不要另开父项。

做完对照关联的目标给两组证据，不准用「编译过了」代替做成：形式证据是测试命令、用例名和结果；实质证据是人拿什么材料、去哪看、怎样算目的发生了。人抽检实质结果之后，才把该项 `patch --status done`，并摘掉 focus。标完成前问：碰到了哪条目标、状态变了没有。然后写下收尾行。

### 流程四：文档不要烂成日记

设计目标只保留目标表、取舍理由与边界。调试、走查、临时配置、做法细节进对应那张项目卡。该项标成完成之后那些细节成为历史，不回写到文首。

发现设计目标已经在追加流水，或文首混了做法细节，模型把过程段搬回对应项。口号和做了一截留在文首，不要搬去项目卡冒充「未完成必须有卡」。

### 流程五：项目目标审计

人说「审计」「目标审计」或「项目目标审计」时走本流程。三阶段按顺序，缺一段就停。结论写在对话里，不写进总表。

**第一阶段：收尾。** 只看 `status=done` 的项。每张卡正文必须有收尾行（「收尾：有」「收尾：没有」「收尾：未碰目标」或「收尾：碰到 …」）。缺这一行就列出来等人补，不进入第二阶段。不靠聊天记忆补「当时问过」。`wont` 和进行中的项不审。

**第二阶段：目标册内部。** 通读总表。条目互相打架时摊开：哪两句不能同时为真、可能是目的改过还是写岔了。问人：留哪句、改哪句、拆成两篇，或确认暂时并存并写明为何。句子过具体、像做法时同样摊开。状态标错（已做成但正文承认没做成，或口号却写成已做成）也摊开。人拍板后才改文首并同步总表。模型不擅自合并。曾经改过目的不是自动失败。

**第三阶段：对照现实。** 用当时的目标册，逐条对照本仓库实现。人指定了产物路径则一并对照；没指定就只审本仓库。按状态给结论：已做成的必须发生，没发生就是退步；做了一截的写清哪截有了、哪截没有；口号记尚未做成，句子仍留在册上。不准只用「编译过了」。

## 产出经过模型时再加厚

改生成规则不能凭「看起来更好」合入。锁住同一份输入、同一套参数、同一个入口；改前跑一次，改后跑一次；拿当天总表上状态为已做成或做了一截的条目并排看，是否变好、有没有把别的打坏。目的若已改，样例也要能检验新目的。换模型时只换模型，不把提示词和参数一起改。

早期不必上复杂评测目录。一份固定样例、两次能复开的运行、并排放着看，就比凭感觉强。

## 新项目第一周

只给从零搭工作法的仓库用。已经在干活的项目不要执行这一节，不要因此建空目录或开第一张卡。

1. 同步个人规则（说话方式、证据、最小改动）。本工作法不代替那些。
2. 建 `docs/能力/`、`docs/方法/`、`docs/看板/`，写一句当前目的（`README.md` 与 `.myrules-context.md`）。
3. 放入本说明书、技能与项目工作法规则。通用红线走 MyRules 的行为规则同步，不写进本仓库。
4. 写第一篇《功能名设计目标》，文首可以只有口号，不放做法。
5. 由模型生成总表，不要手抄。
6. 需要领号时才 `npm run board -- add`。

不要一上来建能力画像长卷、为每张卡预置三节空模板、讨论文稿文件夹当收件箱、或多份必须人手对齐的正文。能力变大、必须深入对照现成系统、或模型输出开始左右对错时，再按上面的流程加厚。

## 空转：骨架有没有配好

不必先写业务代码。用对话试这些事：

- 说「其实我想要的是另一件事」：应先改目标册文首和总表，再问看板上哪些项还做，而不是直接改业务代码。
- 说一句还没人做的目的：应能进目标册，状态为口号，不必先开卡。
- 说「这次挺费事但做完就结束」：直接做。没说登记不要因为费事自己开卡。收工时不新开设计目标。
- 说「动手」「修这个 bug」「去改一下」：直接改，不要先开卡，也不要先问要不要开卡。
- 说「先登记」修旧功能的 bug 或补刀：挂在相关旧项下当子项，不要 `board add` 新父项。
- 说「开一项」并且是一件新事：才 `board add`。人没说登记却自行开父项，算失败。
- 往设计目标里塞走查记录或做法细节：应挪到对应那张卡。口号不要挪走。
- 说「这项做完了」：应问碰到哪条目标、状态变了没有，并写下收尾行；不应把切篇、字段、prompt 写成目标，也不应去另开脱离这张卡的文件。
- 说「审计」或「目标审计」：应按三阶段做；done 项缺收尾行时应先列出来停下；对照现实时按状态给结论，不要把口号从总表拿掉。

有一件直接动手、不走流程，就是常驻规则写长了被忽略，或技能描述没打中人的原话。把守门规则收短，把技能描述写得更像实际会说的那几句。
