# 项目工作法 · 执行细节

工作法理由与原则在 `docs/方法/myrules-项目工作法.md`。落地位置见 `docs/方法/myrules-runtime.md`。这里只放动手时要核对的步骤。

先读仓库根 `.myrules-runtime.json`。下面按 runtime 分支；不要把 agent 的登记命令套到 project 上。

## 路径与命令

| 资产 | 路径 |
|------|------|
| 某篇设计目标（目标册分组） | `docs/能力/<功能名>/<功能名>设计目标.md` |
| 总表 | `docs/设计目标检查清单.md` |
| 空白模板 | 本目录 `templates/`（设计目标、检查清单、看板卡） |

新建设计目标时，先复制对应模板。不要去卡片目录里挑今天干什么。不要把讨论文稿当收件箱。没说登记，不要为了走流程去开卡。修 bug、补刀有相关旧项时，写进旧卡（或挂子项），不要另开父项。口号进册要人点头，不要从讨论文稿爬进去。

### agent

| 资产 | 路径或命令 |
|------|------|
| 进行中的看板卡 | `docs/看板/items/item-N.md`（页眉经脚本改，正文按普通 markdown 改） |
| 登记 / 改页眉 | 只走 `npm run board -- add` / `patch` / `summary` / `next` / `get`。不要手改页眉 |
| 看板页 | `npm run board:server` → http://localhost:8080/（上方只读目标面，按状态列目标册） |

`placement` 可空。若填写，只能是 `改承诺`、`新承诺`、`只记工作`。前两个必须有 `--goal`。

### project

| 资产 | 路径或命令 |
|------|------|
| 进行中的卡 | `ledger/board/`。怎么测写在 `ledger/ops/`。不要把 draft 当规格 |
| git 看板 | `docs/看板/items/` 是归档：`done` / 收尾才必须出版 |
| 登记 | 在 `ledger/board/` 写卡。不要要求跑 `npm run board` |
| 出版文首 / 总表 | 人点头后只派 `myrules-publisher`。coordinator 和本地主会话不要自己改文首 |

## 流程一：目的变了

1. 改目的不必先开卡，也不必先做成。口号可以先写入目标册。人说先登记才挂看板。
2. 用三步判断（先过目的/做法关）决定：改旧句或状态、加进旧篇、还是新开一篇。不写做法。
3. 起草文首表：实质结果置顶；拦住殿后；每条有状态（口号 / 做了一截 / 已做成）、「对比时看什么」和验证方式；项目列可空。
4. 等人确认措辞和状态。
5. **agent：** 原地替换文首。同一轮改总表对应行，必要时改 `.myrules-context.md`。**project：** 人点头后派 `myrules-publisher` 写入 git 文首和总表，必要时同一轮更新 `.myrules-context.md`。coordinator / 主会话不要自己改文首。
6. 只看 focus，以及标题明显对着刚改那条目标的进行中项：这摊还做不做、要不要改范围或关掉。不翻 done 卡。若这次改口作废了碰到的旧卡做法，在那张卡上加一行「已由 … 替代」。不为了留痕通读全部历史卡。

## 流程二：借鉴现成系统

1. 只读人打算搬的那一部分代码，以及能说明「为什么」的提案、变更说明、提交记录。
2. 输出机制说明；每条标「对方写明」或「从代码推断」。
3. 等人逐项采纳 / 砍掉 / 后置。理由指向本项目当前目的。
4. **agent：** 主会话写入文首并同步总表；看板需要时用 `npm run board` 补 `goal`。**project：** 人点头后只派 `myrules-publisher` 写入 git 文首和总表。coordinator / 本地主会话不要自己改文首。不要用看板脚本或 `--goal` 当必做命令。
5. 若学到的东西改变了目的，先走流程一。

## 流程三：写代码（仅当已经挂在某张卡上）

没有看板项就直接改，不要为了走本流程去开卡。

1. 现场写在当前卡或子项。修 bug 挂在相关旧项下，不要 add 新父项。
2. 通读周围实现。说明将改的文件、故意不做的范围。
3. 只改当次需要的行。无关问题记在卡上。
4. 行为变了就跑相关测试。
5. 对照目标汇报：形式证据；实质核验路径。禁止只说编译过了。
6. 问碰到了哪条目标、状态变了没有。做法只关卡。
7. 写下收尾行（旧格式「有 / 没有」或「未碰目标」或「碰到 ID（状态）」）。

### agent 收工

8. 人确认实质结果后：`npm run board -- patch --id item-N --status done --set focus=false`。

### project 收工

8. 人确认实质结果后：改 `ledger/board/` 当前卡为完成。不要跑 `npm run board`。

## 流程四：设计目标不要写成日记

从《功能名设计目标》里删掉调试日志、走查、某日记录和做法细节，移到对应那张看板卡。口号和做了一截留在文首。下一轮读到卡上这些句子，先看有没有替代行，有则跳过。

若文首出现两套对不上的目的，提议拆成两篇，等人拍板后再拆。

## 流程五：项目目标审计

人说「审计」「目标审计」或「项目目标审计」时走这里。三阶段按顺序，缺一段就停。结论写在对话里，不写进总表。

1. **收尾。** 列出全部 `status=done` 的项。每项找收尾行。缺的列出来停下。不靠聊天记忆。不审 `wont` 和进行中的项。通读只为确认收尾行。卡上方案、字段、某日拍板，有替代行的不当现行。
2. **目标册内部。** 通读总表，找出不能同时为真的句子、过具体像做法的行、状态标错的行。摊开问人。人拍板后：**agent** 改文首并同步总表；**project** 派 `myrules-publisher` 出版，coordinator / 主会话不要自己改文首。曾经改过目的不是自动失败。
3. **对照现实。** 查结果是否撑住目标句。已做成的按「对比时看什么」看结果；对不上写在对话里，不写进总表。做了一截的写清动作做到哪。口号记尚未动手，句子留在册上。人给了产物路径则一并对照；没给就只审本仓库。

## 改完一轮的核对

- [ ] 没说登记，就没有为了改代码去开卡，也没有先问要不要开卡
- [ ] 若登记的是修 bug / 补刀：挂在相关旧项下，没有另开父项
- [ ] 若有当前项：现场在那张卡或子项，没有另挂指针，没有预置三节
- [ ] 若目的句变了：`.myrules-context.md` 已改（project 由 publisher 在出版目的时同一轮改）
- [ ] 若动了目标：已说明 focus 和明显相关进行中项的去留；碰到的过期做法已留替代行
- [ ] 没有把走查或做法细节写进文首；没有把口号搬去项目卡冒充必须有活卡
- [ ] 没有把卡片目录当收件箱
- [ ] 若当次挂在看板上：形式证据和实质核验路径都在；完成后该项已 `done`，卡上有收尾行，且问过碰到哪条目标
- [ ] 若在做审计：三阶段按顺序；缺收尾行未跳到对照代码；结论未写入总表；对照按状态给结论

### agent 核对

- [ ] 若动了目标：文首已改（含状态，没有做法细节），总表已逐字同步。登记/改页眉只走了 `npm run board`

### project 核对

- [ ] 若动了目标：已派 `myrules-publisher` 出版文首和总表。coordinator 和本地主会话没有自己改文首
